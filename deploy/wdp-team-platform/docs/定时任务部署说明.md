# 主 Agent 定时任务 · 部署运维说明

> 面向运维/管理员。本地测试用内置调度线程；正式部署到公网/K8s 时按本文处理。

## 一、这套东西是什么

工作台内置了「主 Agent 定时任务」功能（管理入口：左侧导航「团队 Agent」→ ⏰ 主 Agent 定时任务）：
- 4 个内置任务：信号清洗 / 需求停滞提醒 / 周报生成 / session 归档
- 支持 admin 新建「自定义任务」（自然语言 prompt）
- 每个任务：开关（默认全关）、cron 周期、参数/内容、立即运行、看结果

**调度由 web-ui 进程内的后台线程执行**（`api/team_scheduler.py`），跟 web-ui 一起启停。

## 二、关键部署问题与处理

### 问题 1：多副本重复执行（必须处理）

线上 web-ui 通常跑 **2+ 副本**（负载均衡/高可用）。调度线程会**每个副本各跑一次**，导致同一任务被重复执行（周报生成 2 次、通知发 2 遍）。

**解决：用环境变量 `WDP_SCHEDULER_ENABLED` 单点开启。**

```yaml
# 只在其中一个副本（或专门的主 Agent Pod）开启调度：
env:
  - name: WDP_SCHEDULER_ENABLED
    value: "1"     # 主 Pod：开
# 其它 web-ui 副本：
  - name: WDP_SCHEDULER_ENABLED
    value: "0"     # 从 Pod：关（只提供 UI/API，不跑调度）
```

- `WDP_SCHEDULER_ENABLED=0` → 该副本不起调度线程（UI 里任务照常能看/能开关/能手动运行，只是不自动触发）
- 不设该变量 → 默认开（适合本地/单副本）

**推荐架构**：设计文档里主 Agent 是「1 个独立部署、公共 Key、后台全局视角」。最干净的做法是**单独跑一个主 Agent Pod**（`replicas: 1`），只有它设 `WDP_SCHEDULER_ENABLED=1`，其它面向用户的 web-ui 副本全设 `=0`。

### 问题 2：任务配置持久化

任务配置存 `knowledge/team-tasks.json`（随 knowledge 卷）。已加入 `.gitignore`（运行时状态，不进 git）。

- **多副本共享**：knowledge 挂在 RWX 的 PVC 上，所有副本读同一份配置 ✓
- **admin 在 UI 改配置** → 写入 PVC 上的 team-tasks.json → 主 Pod 的调度线程下次 tick（30s 内）读到最新配置 ✓

### 问题 3：进程重启不漏跑/不重复

调度用 `last_run` 时间戳判断，croniter 算「上次运行→现在」之间是否跨过 cron 点。进程重启后从 `last_run` 恢复，30 秒内补上错过的触发，不会因为重启漏跑或在同一分钟重复跑。

## 三、两种部署方案（二选一）

### 方案甲（推荐）：内置调度线程 + 单点开启

- 什么都不用额外装，web-ui 镜像自带
- 主 Pod 设 `WDP_SCHEDULER_ENABLED=1`，其它 `=0`
- 优点：自包含、配置和执行统一、admin UI 实时生效
- 适合：绝大多数情况

### 方案乙：K8s CronJob（云原生，可选）

如果你们规范要求用 K8s 原生调度：
1. 所有 web-ui 副本设 `WDP_SCHEDULER_ENABLED=0`（关掉内置调度，只保留 UI/配置）
2. 用 K8s CronJob 调 `scripts/main_agent_tasks.py`：

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: wdp-signal-clean
spec:
  schedule: "0 9 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: task
            image: <your-webui-image>
            command: ["python3", "/app/scripts/main_agent_tasks.py", "signal-clean"]
            env:
              - name: HERMES_KNOWLEDGE_DIR
                value: /data/knowledge
              - name: HERMES_PROFILES_DIR
                value: /data/profiles
            volumeMounts:
              - name: knowledge
                mountPath: /data/knowledge
          restartPolicy: OnFailure
          volumes:
            - name: knowledge
              persistentVolumeClaim:
                claimName: wdp-team-knowledge
```

- 缺点：cron 周期要在 K8s yaml 和 UI 两处维护（UI 的开关/周期对 CronJob 不生效）；不支持自定义 prompt 任务
- 适合：强制要求 K8s 原生调度、不需要自定义任务的场景

**建议：用方案甲**，除非有硬性云原生规范。

## 四、自定义 prompt 任务的执行（当前状态 + 后续）

- **内置 4 任务**：确定性脚本逻辑，不需要 LLM，进程内直接执行，已完整可用。
- **自定义 prompt 任务**：目前**只登记 prompt，标记 `pending_agent`，不自动跑 LLM**（本地未接主 Agent 的 LLM 调用）。

**后续接主 Agent 的方式**（部署时按需实现，二选一）：
1. 让主 Agent Pod 的调度在触发自定义任务时，把 prompt 投递到主 Agent 的 inbox/会话，由主 Agent 用团队公共 Key 执行。
2. 调度线程直接调用 hermes agent SDK 跑 prompt（需在主 Pod 装 agent 依赖 + 配公共 Key）。

内置任务不受此限制，开箱即用。

## 五、快速核对清单（部署时）

- [ ] knowledge PVC 是 RWX（多副本共享 team-tasks.json）
- [ ] 主 Pod（或单副本）设 `WDP_SCHEDULER_ENABLED=1`，其它副本 `=0`
- [ ] 确认 croniter 已装（web-ui 依赖，`pip show croniter`）
- [ ] 首次部署后，admin 登录 → 成员管理 → 按需开启任务 + 调周期
- [ ] （可选）如需自定义 prompt 任务真正执行，按第四节接主 Agent
