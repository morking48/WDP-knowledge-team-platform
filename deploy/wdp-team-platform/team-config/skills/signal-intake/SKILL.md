# Signal Intake · 信号清洗

> 产品团队 AI Native 工作流的第一层：信号层。
> 多源原始信息格式不一、噪声多、重复多，需要清洗成结构化信号，供后续需求 triage 使用。

## 什么时候用这个 skill

- 用户提供了一段原始信息（会议纪要、客户反馈、聊天记录、语音转写文字）
- 用户明确说"帮我整理成信号"、"清洗这段信息"、"提取需求信号"
- 定期需要把某个来源（如周会纪要、客户拜访记录）转成信号入库

## 输入

任意形式的原始信息文本，可能包含：
- 会议纪要（多人对话、议题跳跃）
- 客户反馈（口语化、情绪化）
- 聊天记录（碎片、重复、离题）
- 语音转写（断句乱、有错别字）

## 输出

一条或多条**结构化信号**，写入 `knowledge/signals/YYYY-MM-DD-<简短标识>.md`，frontmatter 格式：

```yaml
---
id: SIG-YYYYMMDD-NNN          # 信号编号
date: YYYY-MM-DD              # 信号采集日期
source: 会议纪要|客户反馈|聊天记录|语音|其他   # 来源类型
source_ref: <原始信息来源说明，如"2026-07-20 客户A拜访纪要">
title: <一句话概括信号，≤30字>
category: 需求信号|问题信号|趋势信号|风险信号
urgency: 高|中|低
confidence: 高|中|低           # 信息可信度（一手客户 > 转述 > 推测）
related_module: <相关产品模块，如"知识工坊/编辑器/AES底板">
status: 待triage|已转需求|已归档
raw_excerpt: <原始信息关键摘录，1-3句>
---
```

正文：
```markdown
## 信号内容
<结构化描述信号，2-4句话讲清楚是什么>

## 关键事实
- <从原始信息提取的客观事实1>
- <客观事实2>

## 推测与待验证
- <从信号延伸的推测，需后续验证>

## 原始信息
<details>
<summary>点击展开原始信息</summary>

<完整原始文本>
</details>
```

## 执行步骤

1. **通读原始信息**，识别其中有价值的信号点（一个原始信息可能包含多条信号）
2. **分类**：每条信号标记为 需求信号/问题信号/趋势信号/风险信号
3. **评估**：标注 urgency 和 confidence
4. **结构化**：按 frontmatter 字段填写，正文按模板组织
5. **写入文件**：每条信号一个独立文件，文件名 `YYYY-MM-DD-<简短标识>.md`
6. **返回清单**：告诉用户本次清洗出几条信号，文件路径列表

## 清洗原则

- **上下文完整（最重要）**：提炼不许压缩到丢失判断依据——描述里必须带上**谁、什么场合、什么场景下的什么事**（"材质透明问题"✗ → "上海大学项目现场，客户反馈材质透明度调节不生效"✓）。含义多义时宁多保留原文，不猜测归纳。
- **时间性判别**：信号是**新冒出、未定如何执行**的线索（一线反馈/会议流出/刚发现）。内容若带历史背景或进度迭代痕迹（"上次说的""XX有进展"），它不是新信号——提示用户这是已有条目的更新，应走进展合并。
- **保留事实，剔除情绪**：客户说"这破功能太难用了" → 事实是"客户在使用X功能时遇到困难"
- **拆分复合信号**：一条原始信息包含多个独立信号时，拆成多条
- **标注可信度**：一手客户原话 > 销售转述 > 内部推测
- **不做需求判断**：信号层只负责清洗事实，是不是真需求由 triage 层判断
- **保留原始信息**：正文末尾用 `<details>` 折叠保留原文，便于追溯

## 质量检查清单

- [ ] 每条信号都有明确的 source 和 source_ref
- [ ] category/urgency/confidence 三字段都填了，不是默认值
- [ ] 正文"关键事实"是从原文提取的客观事实，不是主观推测
- [ ] "推测与待验证"和"关键事实"严格区分
- [ ] 原始信息完整保留在折叠区
- [ ] 文件命名规范：`YYYY-MM-DD-<简短标识>.md`
