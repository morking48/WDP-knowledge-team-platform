# Requirement Triage · 需求校验建档

> 产品团队 AI Native 工作流的第二层：需求层。
> 信号 → 候选需求 → 人工快速校验 → 建档入库 → 自动分配给对应负责人。

## 什么时候用这个 skill

- `knowledge/signals/` 里积累了若干条"待triage"状态的信号
- 用户明确说"帮我把这些信号转成需求"、"做需求 triage"
- 定期（如每周）需要把新信号归并成候选需求

## 输入

- `knowledge/signals/` 目录下 status 为"待triage"的信号文件
- 或用户直接提供的若干条信号描述

## 输出

**候选需求档案**，写入 `knowledge/requirements/REQ-YYYYMMDD-<简短标识>.md`，frontmatter：

```yaml
---
id: REQ-YYYYMMDD-NNN          # 需求编号
date: YYYY-MM-DD              # 建档日期
title: <一句话需求标题，≤30字>
status: 待校验|已确认|设计中|研发中|已上线|已关闭
priority: P0|P1|P2|P3
source_signals: [<关联的信号ID列表>]
related_module: <相关产品模块>
owner: <负责人，待分配>
customer: <来源客户，如有>
business_value: <业务价值描述，1-2句>
effort_estimate: 待评估|小|中|大
target_release: <目标版本，如"WDP5.16">
tags: [<标签列表>]
tracking:
  - date: YYYY-MM-DD
    event: 建档
    note: 由 signal-intake 转入
---
```

正文：

```markdown
## 需求描述
<用 2-4 句话描述需求是什么、解决什么问题>

## 业务价值
<为什么值得做，对客户/产品/公司的价值>

## 来源信号
<列出支撑这个需求的信号，含信号ID和关键摘录>
- [[SIG-20260720-001]] <信号标题> - 关键事实摘录
- [[SIG-20260720-003]] <信号标题> - 关键事实摘录

## 需求边界
**范围内**：
- <明确包含的内容>

**范围外**：
- <明确不包含的内容，避免范围蔓延>

## 待澄清问题
- [ ] <需要进一步确认的问题1>
- [ ] <问题2>

## 人工校验记录
<人工校验后填写>
- 校验人：
- 校验日期：
- 校验结论：确认 / 打回（原因） / 需补充信息
- 校验意见：

## 后续跟踪
<需求全生命周期的状态变更记录，由 release-tracking skill 自动维护>
```

## 执行步骤

1. **读取信号**：扫描 `knowledge/signals/` 下 status=待triage 的信号
2. **归并信号**：把指向同一问题/需求的多条信号归并为一个候选需求
3. **起草候选需求**：按模板生成 frontmatter 和正文初稿
4. **推送人工校验**：列出候选需求清单（标题+业务价值+来源信号数），请用户快速校验
   - 用户可逐条：确认 / 打回 / 需补充信息
5. **建档**：校验通过的正式建档，写入 `knowledge/requirements/`
6. **更新信号状态**：把已转需求的信号 status 改为"已转需求"
7. **建议分配**：根据 related_module 建议 owner（产品负责人最终拍板）

## triage 原则

- **保留人工快速校验入口**：人能一眼确认"是不是真需求、归类对不对"，校验成本要低
- **可追溯**：每个需求都能追溯到源信号，每个信号都能追到原始信息
- **合并同类项**：多条信号指向同一需求时合并，避免需求池臃肿
- **明确边界**：每个需求必须写清楚"范围外"，防止范围蔓延
- **待澄清问题显式列出**：不把模糊点藏着，明确标出需要进一步确认的问题

## 质量检查清单

- [ ] 每个候选需求都关联了至少一条源信号
- [ ] 业务价值写得具体，不是"提升体验"这种空话
- [ ] 需求边界（范围内/范围外）都写了
- [ ] 待澄清问题显式列出
- [ ] 人工校验记录字段留空待填
- [ ] 已转需求的信号 status 已更新
- [ ] 文件命名规范：`REQ-YYYYMMDD-<简短标识>.md`
