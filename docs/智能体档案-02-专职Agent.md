# 专职 Agent 设计、完成度分析与优化建议

> WDP 团队 AI 工作台 · 智能体留档 · 第 2 篇：4 个专职 Agent
> 版本：v1.0 · 基线日期：2026-07-28 · 依据：代码实证
> **重要说明**：这 4 个 agent 无 Hermes 官方参考，完全基于团队任务需求自研，**成熟度普遍偏低**，本篇逐一诚实分析完成度并给出优化建议。

---

## 〇、总览

| Agent | kind | 定位 | 触发方式 | 完成度（诚实评分） |
|---|---|---|---|---|
| 归并助手 | merge | 分析信号池找可合并组 | admin 手动点 | **60%** 能用但被动、无落地闭环验证 |
| 审核助手 | review | 审一条入库申请 | admin 手动点 | **65%** 结构最全，但查重弱、无主动 |
| 团队规则助手 | rules | 对话共创团队 SOUL | admin 手动点 | **70%** 定位清晰，风险在"全文重写" |
| 团队技能助手 | skill | 对话编辑团队 skill | admin 手动点 | **70%** 同上，结构完整 |

**共性架构（4 个都一样）**：
- 都是**弹窗对话式**，admin 在团队 Agent 页发起，多轮对话
- 都**直连 OpenRouter**（`_call_llm`），**不走官方 AIAgent**，无工具、无 terminal、纯文本进出
- 都用 **proposal 机制**：每轮回复末尾输出 ```proposal JSON 代码块，admin 满意后点按钮落地
- 都有 **L3 稳态 loop**：proposal 格式非法自动带错误提示重试 1 次
- 都注入 **few-shot 历史决策**（`few_shot_block`），理论上越用越懂团队风格

## 一、归并助手（merge）· 完成度 60%

### 1.1 设计意图
信号池积累多了会有重复/相关信号，让 agent 自动找出"应该合并成一条"的分组，减少人工比对。

### 1.2 已实现（代码实证）
- system prompt 注入**当前活跃信号池全量 JSON**（过滤已转需求/已合并）+ 归并规则（可 admin 编辑）+ 历史决策 few-shot
- proposal 格式：`{groups:[{signal_ids, suggested_title, suggested_body, suggested_urgency, reason}]}`
- 多轮对话：admin 可否决某组、要求改标题，agent 吸收更新
- 落地：admin 点确认 → 真执行合并（生成新信号、源信号标记已合并）

### 1.3 完成度分析（缺什么）
| 维度 | 状态 | 问题 |
|---|---|---|
| 核心分析能力 | ✅ 能跑 | 基本可用 |
| **主动性** | ❌ 无 | 纯被动，admin 不点就永远不分析。信号堆积无人提醒 |
| **规模** | ⚠️ 隐患 | 信号池全量塞进 prompt，信号多了（几百条）会撑爆 context |
| **落地验证** | ⚠️ 弱 | 合并后无"合并质量回检"，错合了只能人工发现 |
| **自学习** | ⚠️ 空转 | few-shot 机制在，但当前 0 条历史，等于没生效；且需要 admin 每次决策都被正确记录才积累 |

### 1.4 优化建议（按优先级）
1. **【高】加主动提醒**：配合定时任务——信号池活跃数超阈值（如 >10）或有明显重复时，自动通知 admin"建议归并"，而不是等人点。
2. **【中】信号池分批/预筛**：先用代码做粗筛（按 module/category 分组），只把疑似同组的喂给 LLM，既省 token 又提准。
3. **【中】落地后质量回检**：合并执行后，让 agent 复核一次"合并后的标题/描述是否真的涵盖了源信号"，异常则提示。
4. **【低】确认 few-shot 真在记**：验证每次归并决策都写进 merge.jsonl，否则自学习永远空转。

## 二、审核助手（review）· 完成度 65%（4个里结构最全）

> **2026-07-28 更新**：本轮已做①删死代码 ②驳回体验改进 ③端到端主干实测。详见 2.5。

### 2.1 设计意图
成员提交入库申请后，admin 要判断质量/是否重复/归哪类/派给谁。让 agent 先分析给建议，减轻 admin 负担。

### 2.2 已实现（代码实证）
- system prompt 注入最全：审核规则（可编辑）+ few-shot + **待审申请全文** + **现有知识库条目清单（查重参考，含项目）** + **团队成员职责花名册**（分配依据）
- proposal 格式最丰富：`{suggested_category, duplicate_risk, duplicate_of, quality_notes, recommendation, suggested_owner, suggested_reject_reason}`
- 支持"建议负责人"——对照成员职责给派单建议，这是亮点
- 落地：admin 采纳建议 → 审核通过入库/驳回通知提交人

### 2.3 完成度分析
| 维度 | 状态 | 问题 |
|---|---|---|
| 分析维度 | ✅ 全 | 质量/查重/归类/派单四合一，设计完整 |
| **查重能力** | ⚠️ 弱 | 靠把知识库条目**标题清单**塞进 prompt 让 LLM 肉眼比对，条目多了（>50 截断）漏查重；无语义查重 |
| **主动性** | ❌ 无 | 同归并，纯被动。新申请进来不会自动提示 admin |
| **派单准确性** | ⚠️ 依赖 | 建议负责人质量完全取决于成员职责登记是否完整（team_roster），登记空则派单瞎猜 |
| **自学习** | ⚠️ 空转 | review.jsonl 当前空（测试清掉了），few-shot 无数据 |

### 2.4 优化建议
1. **【高】主动派活**：新入库申请到达时，agent 自动预分析并把建议推给 admin（决策中心角标已有，可再进一步推送 proposal 摘要）。
2. **【高】查重升级**：条目多时，先用代码按 category/关键词粗筛候选，再让 LLM 精判；避免"全量塞 prompt + 截断 50 条"漏查。
3. **【中】职责登记闭环**：派单质量依赖 team_roster，应确保成员职责有登记入口且被填充（结合对话 agent 的画像沉淀能力打通）。
4. **【中】驳回理由质量**：driven 驳回建议应更具体可操作（当前是自由文本，可加"缺哪个字段/哪里不清晰"结构化）。

### 2.5 本轮已做（2026-07-28）
**背景**：核对时发现审核助手实际只有 **1 个活跃入口**（决策中心「🧐 与 Agent 协作审核」多轮对话版，wb5.js→agent_dialog.py），另一套 one-shot 版（`analyze_review`/review-assist）是早期残留死代码（前端零调用），wb2.js 的 `__wbReviewAdvice` 也是永远为 null 的残骸。这是"两套实现"的认知陷阱来源。

**已完成**：
1. **删死代码**：移除 `merge_agent.analyze_review` 函数、`/api/admin/team-agent/review-assist` 路由、`__wbReviewAdvice` 残骸引用。消除误导源，降低维护风险。
2. **驳回体验改进**：
   - 规训升级：SOUL 要求 `suggested_reject_reason` 必须**具体可操作**（指出缺什么字段/哪里不清晰/怎么改），不能只写"不符合标准"。
   - 交互升级：对话版驳回时 admin 可在 AI 建议理由上**确认/补充**再发（wbPrompt 预填 AI 理由），空理由兜底为"请完善后重新提交"。
3. **端到端主干实测**（8798 实例，全通过）：提交A/B → 待审列表 → A通过入库(git已提交) → B驳回(带具体理由) → 信号池确认 → 死代码路由已删(返回"未知操作") → 决策记录接口正常。**审核主干链路稳，可部署**。

**未做（诚实：等真实数据再做）**：查重升级、owner 派单落地放宽、few-shot 效果验证——这三个价值都要"知识库积累数据后"才显现，空库阶段做无法验证效果，故推迟到真实使用一段后针对真实案例改。

## 三、团队规则助手（rules）· 完成度 70%

### 3.1 设计意图
团队 SOUL（所有成员 agent 的最高优先级规训）需要持续优化，让 admin 通过对话共创，而不是手写 markdown。

### 3.2 已实现（代码实证）
- 注入**当前团队规则全文**
- proposal = `{soul: 新版全文}`，max_tokens=8000（要输出完整全文）
- 强调"增量优化非推倒重写""面向 AI 可执行"
- 落地：admin 点"应用并发布"→ 写入母本 + 下发所有成员（L5 锚点守护，防误删关键章节）

### 3.3 完成度分析
| 维度 | 状态 | 问题 |
|---|---|---|
| 定位/流程 | ✅ 清晰 | 对话共创 + 发布下发，闭环完整 |
| **全文重写风险** | ⚠️ 高 | proposal 是**整篇 SOUL 全文**，LLM 重新输出时可能**丢失/篡改**未讨论到的章节。虽有"增量优化"提示和 L5 锚点守护，但本质是让 LLM 重写整篇，风险固有 |
| **diff 不可见** | ⚠️ | admin 看不到"改了哪里"的 diff，只能整篇通读判断，容易漏过 LLM 的暗改 |
| **无版本回滚** | ⚠️ | 发布后若发现规则被改坏，无一键回退到上一版 |

### 3.4 优化建议（按优先级）
1. **【高】改增量 patch 而非全文重写**：proposal 改成"针对某章节的修改块"（old→new），而非整篇。既省 token 又杜绝暗改。若架构不允许，至少发布前**展示 diff** 让 admin 确认。
2. **【中】版本快照 + 回滚**：每次发布前自动存一份 SOUL 快照，出问题能回退。
3. **【低】发布前锚点校验前置**：L5 锚点守护现在是发布时拦截，可提前到 proposal 生成后就提示"你这版丢了 XX 章节"。

### 3.5 本轮已做（2026-07-28）
1. **发布前 diff 展示**：规则助手 proposal 落地前，前端做「新版 vs 当前版」行级 diff（新增绿/删除红 + 增删行数统计 + 折叠未变段），admin 一眼看到 LLM 到底改了什么，不再通读整篇猜暗改。
2. **发布前自动快照 + 一键回滚**：save_team_soul/apply-rules 覆盖前自动存带毫秒时间戳的快照（留最近20份）；团队 Agent 页加「↩ 回滚上一版」按钮，回滚到最近一份内容不同的历史版（回滚本身也存快照，可再回滚）。修复了两个实测发现的 bug：①回滚误选到内容等于当前的快照 ②同秒快照文件名冲突。
3. L5 锚点守护（防丢关键章节）本就存在，与 diff/快照形成三重发布安全网。
**实测**：diff 单测通过；快照+回滚 E2E 通过（保存改动→回滚→完全恢复干净版）。

## 四、团队技能助手（skill）· 完成度 70%

### 4.1 设计意图
团队 skill（成员 agent 共享的方法论）需要维护，让 admin 通过对话编辑 SKILL.md，而非手写。

### 4.2 已实现（代码实证）
- 注入**当前 SKILL.md 全文**（草稿优先，否则已发布版）
- proposal = `{skill_md: 新版全文}`，max_tokens=8000
- 强调**必须保留 frontmatter**（成员靠它检索加载）+ 面向 AI 可执行
- 落地：admin 满意 → 存草稿 → 点发布 → 写正式 SKILL.md，成员实时同步

### 4.3 完成度分析
| 维度 | 状态 | 问题 |
|---|---|---|
| 定位/流程 | ✅ 清晰 | 对话编辑 + 草稿 + 发布，且草稿态设计好（可反复改不影响线上） |
| **全文重写风险** | ⚠️ 高 | 同 rules，proposal 是整篇 SKILL.md，LLM 可能丢步骤/破坏 frontmatter |
| **frontmatter 破坏** | ⚠️ | 虽有"必须保留"提示，但无**代码级校验**——如果 LLM 输出的 skill_md frontmatter 格式错，发布后成员检索会失败 |
| **无 diff** | ⚠️ | 同 rules，改了哪看不见 |

### 4.4 优化建议
1. **【高】发布前 frontmatter 硬校验**：代码解析 proposal 的 skill_md，frontmatter 缺 name/description 或格式错就**拒绝发布**并提示 agent 修正（对齐企业规范的 Schema 强约束）。
2. **【中】展示 diff**：发布前给 admin 看新旧 SKILL.md 差异。
3. **【中】草稿版本留存**：多次编辑时保留草稿历史，可对比。

### 4.5 本轮已做（2026-07-28）
1. **frontmatter 硬校验升级**：publish 前真解析 YAML frontmatter，校验 name/description 非空 + 正文非空，缺失/格式错拒绝发布并给具体提示（原来只查"是否 --- 开头"）。防 LLM 改坏 frontmatter 导致成员检索失效。
2. **发布前 diff 展示**：技能助手 proposal 落地前，前端展示「新版 vs 当前 SKILL.md（草稿优先）」行级 diff，复用 wbLineDiff。
3. 草稿态 + .bak 备份本就存在。
**实测**：frontmatter 校验 E2E 通过（缺name/无frontmatter/正文过短均 422 拒发，合法 200 通过）。

## 五、四个 Agent 的共性问题与系统级建议

### 5.1 共性硬伤（4 个都有）
| 问题 | 说明 | 系统级优化 |
|---|---|---|
| **全被动** | 4 个都要 admin 手动点才动，无任何主动性 | 配合定时任务做"主动预分析+推送"层：新申请自动预审、信号堆积自动提醒归并 |
| **自学习空转** | few-shot 机制都在，但依赖决策被正确记录，当前数据几乎为 0 | 确保每次 admin 决策都写进对应 jsonl；上线跑一段时间才能看出效果 |
| **无工具/纯文本** | 都不走 AIAgent、无 terminal、无脚本调用 | 可让它们调用 query_knowledge.py --json 拿结构化数据（比塞 prompt 更准），但需先加 --json 模式 |
| **规模隐患** | merge/review 把知识库/信号池全量塞 prompt | 数据量上来后必须改"代码粗筛 + LLM 精判" |

### 5.2 与企业级 Agent 规范的差距（对照你提供的规范）
| 规范条款 | 4 个 agent 现状 | 差距 |
|---|---|---|
| Schema 强约束 + 校验失败自动修正 | proposal 有格式校验 + L3 重试 1 次 | ✅ 基本符合（rules/skill 差 frontmatter 校验） |
| 工具容错返回结构化错误 | LLM 调用失败返回 error，不崩 | ✅ 符合 |
| 收敛条件（max_iterations≤3） | L3 只重试 1 次 | ✅ 符合甚至更保守 |
| 确定性逻辑用代码 | 合并/入库执行是代码，LLM 只给建议 | ✅ 符合 |
| **Reflection 外部 Evaluator** | 无落地后质量回检 | ❌ 缺（建议 1.3/2.3 提到） |
| **可观测/Trace** | 有决策日志(jsonl)但无完整 trace | ⚠️ 部分 |

**结论**：4 个 agent 在"控制流安全"上意外地比较规范（proposal 校验、重试上限、代码执行确定性逻辑），**真正的短板在"能力完整度"**——被动、自学习空转、查重/规模弱、rules/skill 的全文重写风险。

## 六、优化优先级总表（跨 4 个 agent）

| 优先级 | 优化项 | 涉及 agent | 价值 |
|---|---|---|---|
| P0 | rules/skill 发布前 frontmatter 校验 + diff 展示 | rules, skill | 防暗改/破坏，风险最高 |
| P0 | 主动预分析层（新申请自动预审、信号堆积提醒） | merge, review | 从"被动工具"变"主动助手"，价值最大 |
| P1 | 查重/归并升级为"代码粗筛+LLM精判" | merge, review | 解决规模隐患+提准 |
| P1 | 确认 few-shot 真在积累决策 | 全部 | 自学习不空转 |
| P2 | rules/skill 版本快照+回滚 | rules, skill | 容错 |
| P2 | 让 agent 调 query_knowledge --json 拿结构化数据 | merge, review | 比塞 prompt 更准（需先加 --json） |

## 七、给用户的核心判断（诚实结论）

1. **这 4 个 agent "能用但不够聪明"**——控制流做得规范（不会崩、不会乱执行），但**都是被动的、自学习还没真正跑起来、rules/skill 有全文重写的固有风险**。
2. **最该先补的是两件事**：① rules/skill 的**发布前校验+diff**（防把规则/技能改坏，这是安全底线）② **主动预分析层**（让 review/merge 不用人一直点，价值最大）。
3. **自学习(few-shot)是设计亮点但需要时间**——机制在，但要上线真实使用、积累几十条决策后才看得出"越用越懂团队"的效果，现在评判为时过早。
4. **规模问题目前不痛**（数据量小），但**信号/需求上百条后 merge/review 会撑爆 prompt**，属于"现在不痛、必然要改"的技术债，建议数据量起来前就把"代码粗筛"补上。
