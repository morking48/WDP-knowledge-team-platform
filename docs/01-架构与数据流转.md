# 架构与数据流转

## 1. 整体架构

```
┌─────────────────────────────────────────────────────────┐
│  团队成员入口（各自选顺手的）                              │
│  企业微信 / Web浏览器(WebUI) / 飞书 / 邮件                 │
└──────────────────┬──────────────────────────────────────┘
                   │  Hermes Gateway（多平台网关）
┌──────────────────▼──────────────────────────────────────┐
│  Hermes Agent（部署在你们服务器）                         │
│  ├─ 团队共享 Skills 库（本仓库 skills/）                   │
│  ├─ 团队共享 Memory（产品知识/决策/口径）                  │
│  ├─ Sessions 历史（工作过程留痕，可检索）                  │
│  └─ Cron 定时任务（信号收集/节点跟踪/数据同步）             │
└──────────────────┬──────────────────────────────────────┘
                   │
┌──────────────────▼──────────────────────────────────────┐
│  数据层（全部在你们服务器）                                │
│  ├─ 本仓库 knowledge/ 目录（Markdown + git）              │
│  ├─ SQLite 会话库（sessions/messages）                    │
│  ├─ 挂载现有系统：需求池/文档库/研发进展/NFS                │
│  └─ 模型：外部API 或 内网本地模型                          │
└─────────────────────────────────────────────────────────┘
```

## 2. 关键机制映射（四层闭环 → Hermes 能力）

| 闭环层 | Hermes 实现 | 数据流转 | 产出落点 |
|---|---|---|---|
| 信号层 | Cron 定时任务 + `signal-intake` skill | 多源（会议纪要/客户反馈/需求池/研发进展）→ 结构化信号 | `knowledge/signals/` |
| 需求层 | `requirement-triage` skill + 企微推送人工校验 | 信号 → 候选需求 → 人工一键确认 → 建档 | `knowledge/requirements/` |
| 产品设计层 | `prd-writing` + `design-handoff-to-dev` skill | 需求 → 面向 agent 完整设计 → 研发交付物 | `knowledge/designs/` |
| 跟踪层 | `release-tracking` skill + Cron 每日扫描 | 到节点/超期/停滞 → 企微提醒；上线效果回流成新信号 | `knowledge/tracking/` |

## 3. 数据流转原则

- **单一数据源**：所有团队知识资产只落在 `knowledge/` 一个目录，git 版本化，不搞第二份清单/备份
- **人工介入点低门槛**：人只在关键处介入（信号确认、需求校验、设计把关），每一步操作成本要低
- **面向 agent 的完整性**：设计稿必须包含 agent 执行所需的全部信息（数据契约/状态/边界/执行规则），通过 skill 模板强制
- **共享记忆**：团队口径/决策/铁律进共享 memory，下次所有人都能用到；个人偏好进各自 profile 的 memory

## 4. 多成员隔离与共享

- 每个团队成员一个 **profile**：独立的 sessions/memory（个人偏好/在跟的事）
- **共享 skills 目录**：所有 profile 挂载同一份 `skills/`（团队方法论统一）
- **共享 knowledge 目录**：所有产出落到同一个 git 仓库（团队资产归一）
