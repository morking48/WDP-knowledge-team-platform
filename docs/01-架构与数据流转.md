# 架构与数据流转

## 1. 整体架构

```
┌─────────────────────────────────────────────────────────┐
│  团队成员入口                                             │
│  Web 浏览器（定制工作台 workbench.html） / 企业微信        │
└──────────────────┬──────────────────────────────────────┘
                   │  定制前端 wb.js~wb5.js 复用后端 API + SSE
┌──────────────────▼──────────────────────────────────────┐
│  定制多用户工作台（web-ui/，复用官方 Hermes 后端）        │
│  ├─ 每成员一个 profile（独立 sessions/memory/个人SOUL）   │
│  ├─ 对话 Agent（官方 AIAgent 内核 + 团队 SOUL 规训）       │
│  ├─ 4 个专职 Agent（归并/审核/规则/技能，直连 LLM）        │
│  ├─ 定时任务（6 内置，纯脚本，默认关）                    │
│  └─ agent 脚本（submit_review/query_knowledge/画像/技能） │
└──────────────────┬──────────────────────────────────────┘
                   │
┌──────────────────▼──────────────────────────────────────┐
│  数据层                                                   │
│  ├─ knowledge/ 目录（Markdown + git，单一数据源）         │
│  │   四层闭环 + 项目分区 + 团队成员 + 母版库              │
│  ├─ hermes-home/（SOUL/config/scripts，运行时状态）       │
│  ├─ SQLite 会话库（sessions/messages）                    │
│  └─ 模型：团队默认(kimi-k3) + 个人渠道(如 copilot) + fallback │
└─────────────────────────────────────────────────────────┘
```

## 2. 智能体架构

### 对话 Agent（主力，每成员一个）
- **内核**：官方 `AIAgent`（run_agent），全功能工具集（terminal/file/web/skills）。
- **规训**：团队 SOUL（标记块，管理员发布同步）+ 个人 SOUL（块外，个人习惯）。团队铁律 > 个人偏好。
- **脚本**（hermes-home/scripts/，靠 HERMES_KNOWLEDGE_DIR 定位）：
  - `submit_review.py` 提交入库 · `query_knowledge.py` 查询知识库
  - `update_member_profile.py` 成员画像 · `save_personal_skill.py` 个人技能
- **能力模式**（对话框强制注入）：🎯 设计模式（design-converge）/ 📥 信号清洗模式（signal-intake）。

### 4 个专职 Agent（admin 用，弹窗对话式，直连 OpenRouter）
| Agent | 作用 | 发布安全网 |
|---|---|---|
| 归并助手 | 信号池分桶粗筛 + LLM 精判 + 结果自校验 | — |
| 审核助手 | 入库审核（质量/查重/归类/派单建议） | 驳回理由须具体可操作 |
| 规则助手 | 对话共创团队 SOUL | 发布前 diff + 快照/回滚 + L5 锚点守护 |
| 技能助手 | 对话编辑团队 skill | 发布前 diff + frontmatter 硬校验 + 草稿/备份 |

## 3. 数据流转（四层闭环 + 项目分区）

| 层/分区 | 实现 | 数据流转 | 产出落点 |
|---|---|---|---|
| 信号层 | signal-intake skill / 📥 模式 | 多源原始信息 → 结构化信号 | `knowledge/signals/` |
| 需求层 | requirement-triage skill + 归并助手 + 决策中心审核 | 信号 → 候选需求 → 人工校验 → 建档 | `knowledge/requirements/` |
| 产品设计层 | design-converge skill / 🎯 模式 | 需求 → 面向 agent 完整设计 | `knowledge/designs/` |
| 跟踪层 | 定时任务扫描 | 需求停滞/周报提醒 | `knowledge/tracking/` |
| **项目分区** | 项目开档 + 信号→项目需求 + 交付材料 | 信号池 → 项目需求(PREQ) → 交付材料(DLV) | `knowledge/projects/<项目>/` |
| 团队成员 | 对话中 agent 强制/主动沉淀 | 能力表现 → 画像（≤150字） | `knowledge/team/` |

**统一提交入口**：成员提交信号/需求/设计 → inbox → 决策中心审核助手分析 → admin 通过入库/驳回 → 通知提交人。
**知识库导航**：`knowledge/index.md` 渐进披露索引，写操作实时刷新 + 定时兜底刷新。

## 4. 数据流转原则

- **单一数据源**：所有团队知识资产只落 `knowledge/` 一个 git 仓库，不搞第二份清单/备份。
- **人工介入点低门槛**：人只在关键处介入（信号确认、需求校验、设计把关、入库审核）。
- **面向 agent 的完整性**：设计稿含 agent 执行所需全部信息（数据契约/状态/边界/执行规则）。
- **可追溯**：需求追源信号（source_signals）、设计追需求（requirement_id）、交付材料追项目需求。
- **团队/个人隔离共存**：团队 SOUL 标记块统一发布（原位替换不冲个人），个人区块外自由，个人 skill 物理隔离。

## 5. 多成员隔离与共享

- 每个团队成员一个 **profile**：独立 sessions/memory/个人 SOUL/个人 skill/个人模型渠道。
- **共享 skills**：所有成员实时扫描同一份团队 `skills/`（方法论统一）。
- **共享 knowledge**：所有产出落到同一个 git 仓库（团队资产归一）。
- **团队默认模型** kimi-k3；成员可在个人中心配自己渠道（如 copilot claude-opus-4.8），三级 fallback。

## 6. 部署形态

- 部署包 `deploy/wdp-team-platform/` **自包含**（web-ui + agent-src 随仓库自带）。
- Dockerfile 以仓库根为构建上下文：`docker build .`，overlay 覆盖官方 web-ui，team-config 注入 SOUL/skill/脚本。
- 三仓库：工程根（GitHub 备份）/ deploy（gitlab platform）/ knowledge（gitlab knowledge）。
