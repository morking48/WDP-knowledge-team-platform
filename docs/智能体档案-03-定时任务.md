# 定时任务智能体设计、完成度分析与优化建议

> WDP 团队 AI 工作台 · 智能体留档 · 第 3 篇：定时任务智能体
> 版本：v1.0 · 基线日期：2026-07-28 · 依据：代码实证（web-ui/api/team_tasks.py + team_scheduler.py）
> **说明**：定时任务是平台的「后台自动化层」，与对话/专职 agent 不同——它**无人值守、按 cron 触发**。本篇诚实评估 7 个内置任务的完成度与真实价值。

---

## 〇、总览

| 任务 | 类型 | 默认 schedule | 触发即生效？ | 完成度 |
|---|---|---|---|---|
| 信号清洗 signal-clean | 纯脚本扫描 | 每天 9:00 | ⚠️ 只出清单，不通知 | 50% |
| 需求停滞 stagnant-req | 纯脚本扫描 | 每天 10:00 | ⚠️ 只出清单，不通知 | 50% |
| 需求周报 weekly-report | 纯脚本统计 | 每周五 18:00 | ✅ 生成 md 文件 | 70% |
| session 归档 session-archive | 纯脚本扫描 | 每周日 3:00 | ⚠️ 只出候选，不实际归档 | 45% |
| 上传处置 upload-review | 纯脚本扫描 + **通知** | 每天 19:00 | ✅ **主动通知 admin** | 75% |
| 清理已删 purge-deleted | 纯脚本执行 | 每天 4:00 | ✅ 真删过期文件 | 80% |
| 刷新索引 refresh-index | 脚本执行 | 每 2 小时 | ✅ 真刷新 + 写操作实时触发 | 85% |

**共性架构**：
- **默认全部关闭**（enabled=false），admin 在团队 Agent 页按需开启/改 schedule/改参数。
- **6 个内置是纯确定性脚本扫描**（无 LLM），只有 admin 新建的**自定义任务**走 LLM（`_run_custom_llm`，团队 key + 默认模型，注入知识库摘要）。
- **调度**：web-ui 内置调度线程（team_scheduler.py），本地默认开，线上多副本用 `WDP_SCHEDULER_ENABLED=0` 关掉非主 Pod。
- **结果落点**：每个任务写 `tracking/<task>-latest.json` + 记录 `last_run/last_result`（团队 Agent 页可查）。

---

## 一、逐个分析

### 1. 信号清洗 signal-clean · 50%
- **做什么**：扫 signals/ 里 status=待triage/待确认的信号，输出清单到 `tracking/signal-clean-latest.json`。
- **真实价值缺口**：名叫"清洗"，实际**只是列出待处理清单，不做任何清洗**（清洗要靠 signal-intake skill + 人/agent）。且**结果不通知任何人**，admin 不主动看 tracking 就等于没跑。
- **诚实评价**：是个"待办统计"，名不副实。价值取决于有没有人去看那个 json。

### 2. 需求停滞提醒 stagnant-req · 50%
- **做什么**：扫 requirements/ 里 N 天（默认7）无更新且未上线/关闭的需求，输出停滞清单。
- **缺口**：**只出清单不提醒**。"提醒"二字没兑现——没有推送给负责人或 admin。逻辑本身是对的（按 mtime 判停滞），但闭环断在最后一步。

### 3. 需求周报 weekly-report · 70%
- **做什么**：统计 signals/requirements/designs 总量 + 状态分布，生成 `tracking/weekly-YYYYMMDD.md`。
- **评价**：这个**真出了产物**（一份周报 md），比前两个完整。但纯数字统计，无洞察（不是 LLM 生成的分析）。适合 admin 周末扫一眼总量趋势。缺口：也不主动推送。

### 4. session 归档 session-archive · 45%
- **做什么**：扫各成员 ≥30 天未活跃的 session，输出**归档候选**清单。
- **缺口**：**只列候选，不实际归档**（代码注释明确"未实际移动"）。完成度最低——它连产物动作都没有，纯粹是个扫描报告。

### 5. 上传处置提醒 upload-review · 75%
- **做什么**：扫各成员 workspace/uploads 里的临时文件，超 N 天（默认3）未处置的，**主动通知所有 admin**（notify_member）。
- **评价**：**7 个里闭环最完整的之一**——真的推送提醒到 admin 铃铛，不用人主动看。价值实在：防上传文件烂在角落没转化进工作台。

### 6. 清理已删内容 purge-deleted · 80%
- **做什么**：真删 `library/archive/_deleted/` 里超 N 天（默认30）的软删除文件。
- **评价**：**真执行、真闭环**（不是扫描是动作）。纯运维清理，稳定可靠，价值明确。

### 7. 刷新知识库索引 refresh-index · 85%（本轮新增）
- **做什么**：重新生成 knowledge/index.md（对话 agent 导航靠它）。
- **评价**：**完成度最高**——不仅定时兜底（每2小时），还被入库/项目写操作**实时触发**（双保险）。真执行、真生效、有实际消费方（对话 agent 查询能力依赖它）。

## 二、共性问题（诚实结论）

| 问题 | 说明 | 影响 |
|---|---|---|
| **"提醒/清洗"名不副实** | signal-clean/stagnant-req 名字承诺了动作，实际只出清单 | 用户期待落空，或以为没生效 |
| **结果无出口** | 除 upload-review 主动通知外，其余结果都埋在 tracking/*.json，无人主动看就白跑 | 6个里4个是"沉默的扫描" |
| **只扫不做** | session-archive 连产物动作都没有 | 完成度最低，接近占位 |
| **纯脚本无智能** | 6个内置都是确定性统计，没有 LLM 的洞察/建议 | 是"定时脚本"，谈不上"智能体" |
| **依赖真实数据** | 空库阶段这些任务跑出来全是 0，看不出价值 | 现在评估/优化都为时过早 |

---

## 三、优化建议（诚实分级）

### 现在不该大改（对着空库优化没意义）
6 个纯扫描任务的价值都要**真实数据积累后**才显现。空库阶段：signal-clean 扫出 0 条、weekly-report 全是 0、stagnant-req 无停滞需求。**现在优化无法验证效果**，违背"难触发就没意义"原则。

### 真正该补的（不依赖数据量，是结构缺陷）
1. **【P1】给"提醒"类任务补通知出口**：stagnant-req、signal-clean 应像 upload-review 一样，扫出结果后**主动通知**（停滞需求推给负责人、待triage信号推给admin），否则"提醒"名不副实。这是结构补全，不依赖数据量。
2. **【P2】session-archive 补实际动作或改名**：要么真归档（移到归档目录），要么诚实改名为"session 清理候选报告"。当前名实不符。

### 真正的"智能化"方向（等平台跑起来再做）
3. **智能日报/周报**：把 weekly-report 从纯数字统计升级为 LLM 生成的分析（用自定义任务的 `_run_custom_llm` 机制已具备能力）——"本周新增 X 需求，Y 条停滞，建议关注 Z"。**这是把"定时脚本"变"定时智能体"的关键**，但要有真实数据才有内容可分析。
4. **智能派单**：新信号/需求进来自动分析该派给谁（结合审核助手的派单能力 + 成员画像）。

## 四、给用户的核心判断

1. **7 个里真正"完整闭环"的只有 3 个**：refresh-index（85%）、purge-deleted（80%）、upload-review（75%）——它们都真执行、有出口。
2. **4 个是"沉默的扫描"**（signal-clean/stagnant-req/weekly-report/session-archive）——逻辑对，但结果埋在 json 里没人看，或名不副实。
3. **"智能体"名不副实**：6 个内置全是确定性脚本，没有 LLM 智能。真正的智能任务能力（`_run_custom_llm`）只在 admin 手动新建的自定义任务里，且要配团队 key 才生效。
4. **最该先补**：给"提醒"类任务加通知出口（P1，结构补全不依赖数据）；**智能化升级等平台真实用起来、有数据可分析再做**。
5. **部署提示**：这些任务**默认全关**，正式部署后 admin 要在团队 Agent 页手动开启需要的。用户已明确"定时任务部署后自己开，我只保证 task 能跑通"——当前 7 个任务的执行逻辑都已验证可跑通（无 LLM 依赖的 6 个稳定；自定义任务需配团队 key）。

## 五、本轮已做（2026-07-28）

用户明确定位：**定时任务 = 确定性脚本，做机械化固定工作，不碰需要人验证的复杂判断**。基于此重新审视第三篇结论——问题不在"不够智能"（那违背定位），而在"机械闭环断在最后一步"。

**已完成**：
1. **删 session-archive**：机械价值最低（只列候选不动数据、扫所有成员 profile 过绕），直接删除。内置任务从 7 个精简为 **6 个**。load_config 加自动剔除逻辑——部署时旧配置里的 session-archive 会被自动清除（不用手动改配置）。
2. **给 3 个"提醒"类任务补通知出口**（照 upload-review 已验证的 notify_member 模式，纯机械、0 条不打扰）：
   - `signal-clean`：扫到待 triage 信号 → 通知 admin
   - `stagnant-req`：扫到停滞需求 → **按负责人分组各自推送** + admin 汇总
   - `weekly-report`：周报生成后 → 通知 admin
   现在"提醒"名副其实——扫描结果自动送达该看的人，不再埋在 tracking/*.json 里没人看。

**未做（符合定位，不该做）**：智能日报/智能派单——那需要人验证、上 LLM，违背"机械化固定工作"定位。

**实测**：内置任务列表 6 个（session-archive 已剔除）；stagnant-req 扫到停滞需求并成功通知 admin（铃铛收到 2 条）；weekly-report 生成并通知。

### 现役 6 个内置任务（精简后）
| 任务 | 机械动作 | 通知 |
|---|---|---|
| refresh-index | 刷新知识库索引 | —（对话 agent 消费） |
| purge-deleted | 真删过期软删除文件 | — |
| upload-review | 扫上传临时文件 | ✅ 通知 admin |
| signal-clean | 扫待 triage 信号 | ✅ 通知 admin |
| stagnant-req | 扫停滞需求 | ✅ 通知负责人 + admin |
| weekly-report | 生成周报 md | ✅ 通知 admin |

全部纯确定性脚本、机械闭环完整、默认关闭（admin 按需开）。
